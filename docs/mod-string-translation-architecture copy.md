## 📖 Mod String Translation Architecture

The localization process for this project utilizes a custom syntax within YAML resource files. This document explains our architectural decision and how you can effectively contribute to translation.

### Why Not Use Standard PO-Files (e.g., Poedit)?

We acknowledge that tools like Poedit and the use of Gettext `.po` files are the preferred industry standard for localization workflows. Initially, we considered adopting this standard approach.

However, we encountered a significant technical challenge: the need for **dynamic, formatted text that includes special function calls** within the translated strings.

Standard PO-files treat translated text as static strings, relying solely on simple positional placeholders (like `{0}`). This structure could not accommodate certain complex formatting functions required by the game's engine, specifically:

* **FormatAsLink:** This function dynamically creates clickable links within the game's text using the pattern `FormatAsLink("Display Name", "Some Link ID")`. The critical issue is that the text that **needs to be translated** is the **"Display Name"** argument *inside* the function call. Static placeholders could not solve this problem, as the entire function call needs to be preserved while only the displayed text is changed.

### The Solution: PowerShell-Inspired Expression Syntax

To resolve this, we devised a custom expression syntax that mimics function calls, drawing inspiration from the PowerShell scripting language.

This syntax allows us to embed translatable text directly as an argument within a function call, ensuring that the function structure is maintained during translation.

The general pattern is:

```plaintext
$(FormatAsLink 'Translated Text' 'Some Link ID') Blah blah...
```

We believe this approach provides a highly **consistent** and **intuitive** method for translators to manage dynamic string resources.

### In Practice: Reviewing the Translation Format

Let's examine a portion of the actual `strings.ko-KR.yaml` file used in the `Advanced Generators` mod to illustrate how this syntax works:

| Key | Korean Source Text (`strings.ko-KR.yaml`) |
| :--- | :--- |
| `0.REFINEDCARBONGENERATOR.NAME` | `$(FormatAsLink '정제 탄소 발전기' $id:RefinedCarbonGenerator)` |
| `0.REFINEDCARBONGENERATOR.DESC` | `$(FormatAsLink '석탄' 'COAL') 발전기보다 더 많은 전기를 생산합니다.` |
| `0.THERMOELECTRICGENERATOR.DESC` | `초당 $(Get-String $var:ThermoelectricGeneratorHeat)kDTU의 열을 제거합니다.` |

When translating this content into English, you maintain the function call structure (`$(Function '...arguments...' )`) and only replace the translatable text (the first argument).

| Key | English Translation Example |
| :--- | :--- |
| `0.REFINEDCARBONGENERATOR.NAME` | `$(FormatAsLink 'Refined Carbon Generator' $id:RefinedCarbonGenerator)` |
| `0.REFINEDCARBONGENERATOR.DESC` | `It produces more electricity than $(FormatAsLink 'Coal' 'COAL') generators.` |
| `0.THERMOELECTRICGENERATOR.DESC` | `Removes $(Get-String $var:ThermoelectricGeneratorHeat)kDTU of heat per second.` |

### Advanced Flexibility

A key advantage of this syntax is that it treats the string resources as executable expressions, not fixed static text. This gives you, the translator, **complete freedom** to adjust sentence structure, word order, and even rearrange dynamic elements to suit the target language's grammar.

For instance, you can combine multiple functions and variables:

```yaml
# Example of combining dynamic calls and text:
0.REFINEDCARBONGENERATOR.DESC: "$(Get-String $id:RefinedCarbonGenerator) and my cool kDTU = $(Get-String $var:ThermoelectricGeneratorHeat). $(FormatAsPositiveRate '+1234W')."
```

In the game, this might render as:

```plaintext
RefinedCarbonGenerator and my cool kDTU = 156. +1234W
```

*(Note: The text generated by `FormatAsPositiveRate('+1234W')` would typically appear in a bright cyan color)*

### Important Guidelines for Translation

#### **Variables and IDs (`$id` / `$var`)**

Expressions starting with `$id` or `$var` reference variables or string resources specific to a mod.

* **DO NOT** introduce new `$id` or `$var` references that do not exist in the original `strings.ko-KR.yaml` file you are currently translating. Stick to the variables present in the source.
* The use of these variables is constrained to the mod they originate from.

#### **Non-Translatable Placeholders (`{}` / `<>`)**

Text enclosed in curly braces (`{}`) or angle brackets (`<>`) are special placeholders that are processed by the program (often representing runtime values like wattages, temperatures, or names).

**You must NOT translate these placeholders.**

| Original Korean Text | Correct English Translation |
| :--- | :--- |
| `"와트 수: {Wattage}"` | `"Wattage: {Wattage}"` |
| `"현재 시간: <CurrentTime>"` | `"Current Time: <CurrentTime>"` |
